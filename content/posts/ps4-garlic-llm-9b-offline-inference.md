機房角落那台準備報廢的機器，真的只剩回收一條路嗎？如果採購單上的 GPU 預算被砍掉，資料又明文規定不能出公司，很多部門最後會問的就不是「能不能上雲」，而是「推論的硬體下限，到底還能被拉到多低？」這篇先把定位講清楚：這是一個概念驗證（PoC），不是可交付的伺服器，也不是可以直接放進機房值班的答案。它證明的是一條路走得通，不是 SLA，也不是維運模型。

## 先講結論：它不是把 PS4 變成 AI 伺服器，而是把下限往下推

Garlic LLM 的價值，不在於「遊戲機也能跑 LLM」這種聳動說法，而在於它把推論硬體的下限往下推了一格。根據專案公開資訊，它是單一開發者的個人專案，依賴越獄環境，沒有支援承諾；而且專案跑的是 4.31 bpw 的重打包版，對應的 context 也只有 16K，不是把 Qwen3.5-9B 的原生 262K 能力整包搬上去。也就是說，這裡展示的是「在極限硬體上把模型勉強放進去並跑起來」，不是「把一台 PS4 升級成通用 AI 平台」。

## 不是拔掉既有驅動，而是在沒有 API 的地方自己蓋 runtime

真正有意思的地方，在機制而不是機型。一般推論堆疊會走「模型 → 框架（像 llama.cpp、PyTorch）→ 廠商驅動 → GPU」；但 Garlic LLM 所處的 homebrew PS4 環境，本來就沒有 GPU compute API，也沒有 ML 函式庫。OpenOrbis 的 GPU rendering 甚至還在 roadmap 的 v0.7。於是作者做的不是「繞過驅動」，而是自己把最小 runtime 補起來：把矩陣運算、attention、normalization 寫成 OpenCL C kernel，再用 LLVM 編成 GCN 機器碼，最後手寫 PM4 命令封包，把本來會由驅動層產生的工作自己產生出來。

這一點很重要，因為它把效能來源說清楚了：少掉的不是一層漂亮的抽象，而是整套框架的轉譯、驗證、資源管理與中介成本；換來的是更少的記憶體搬移、直接對硬體排程，代價則是沒有生態系、沒有 fallback、出錯只能自己除錯，而且只能針對單一硬體工作。早期遊戲機開發和 80 年代 demoscene 其實也走過類似路線：把抽象層拿掉，換取每一點效能；但維護成本永遠是，整條鏈只有少數人看得懂。

## 176.0 GB/s 的天花板，為什麼把 31～43 tok/s 推到極限

這篇最值得算的，不是「看起來有多快」，而是它有沒有撞上硬體天花板。先看模型體積：9B 參數如果用 fp16，權重大約 18.0 GB；int8 也要 9.0 GB，都放不進 PS4 的 8 GB。換句話說，4-bit 不是為了漂亮的數字，而是唯一有機會讓 9B 模型住進這台機器的方法。

再看專案實際檔案。公開檔案表把主權重與 MTP head 加總到 4.853 GB；PS4 的記憶體頻寬則是 176.0 GB/s，這個數字可由 [TechPowerUp GPU DB](https://www.techpowerup.com/gpu-specs/playstation-4-gpu.c2085) 與 [Digital Foundry 的規格分析](https://www.gamesindustry.biz/df-hardware-spec-analysis-playstation-4-6) 交叉確認。把 176.0 ÷ 4.853 算下去，得到的不是「單次 pass 的上限」，而是每秒大約 36.3 次完整權重 pass 的理論上限。這就是本篇的核心座標：它不是憑感覺快，而是站在一條可以重算的 roofline 上。

作者自述的速度是一般對話 31～39 tok/s，寫程式時最高 43 tok/s；但這些數字是作者自己量到的，沒有第三方複測，而且測試條件也不完整，prompt 長度、輸出長度、prefill 是否計入都沒公開，所以它不能直接拿去和其他機器做一對一比較。即使如此，拿去對 36.3 這條線，31 tok/s 約是 86%，35 tok/s 約 97%，39 tok/s 約 108%，43 tok/s 約 119%。表面上看起來像是越過天花板，但原因是 MTP 投機解碼：一次 pass 先擬幾個 token，再用同一次驗證流程把多個 token 算進去，所以 39 tok/s 其實只相當於每次 pass 產出約 1.08 個 token，43 tok/s 也只有 1.19 個。這代表接受率不高，但也說明它沒有在硬體之外魔法加速，而是在用演算法把剩餘的算力換成輸出率。

更關鍵的是，沒有 MTP 時只有 22 tok/s，大約是天花板的 61%。這意味著在投機解碼之前，系統比較像是算力或排程受限；到了 31～43 tok/s 之後，才真正貼上記憶體頻寬牆。也因此，這篇文章的結論應該寫成：沒有剩餘頻寬可榨了。36.3 其實還是「權重獨佔全部頻寬」的樂觀值；真實世界裡 KV cache、activation，以及跑在 CPU 上的 tokenizer 和 UI 文字渲染，都會跟 GPU 一起搶同一條 176 GB/s，所以真實天花板只會更低，不會更高。

如果把同樣邏輯放到 PS4 Pro，217.6 GB/s 反推的理論上限約 44.8 tok/s，和官網列出的三位使用者回報、最高 45 tok/s 已經幾乎貼線；官網另外還提到一位使用者的原生模式可到 56 tok/s，但那還在審查中，沒有進正式下載包。這不是在替 Pro 背書，而是在提醒一件事：在這條路上，速度大致就是頻寬的函數。

## 四條限制，才是企業最該拿回去看的部分

第一，這是單一開發者的個人專案，而且依賴越獄環境，不是可交付產品，也沒有任何支援承諾。這代表企業不能把「有人做得出來」直接等同於「我們團隊也能維運」。

第二，31～43 tok/s 只代表速度，不代表可用性。正確率、長上下文、指令遵循都沒有完整評測，所以它不是「跑得動就能上線」，更不是「客服、知識庫、內部助理都能直接接」。

第三，這個案例的價值是驗證邊界，不是背 SLA。因為它的前提就是越獄、支援清單內的韌體、以及一台願意被拿來做實驗的硬體；一旦你要的是 24×7、可稽核、可交接、可更新模型，這條路就會立刻變得很重。

第四，所有硬體數字都不能離開來源單獨看：176.0 GB/s 要回到 TechPowerUp 與 Digital Foundry，4.853 GB 要回到專案公開檔案表，16K context 與非原版權重也要一起讀。沒有這些上下文，就很容易把「能跑」誤寫成「跑滿」，把 PoC 誤寫成產品。

## 企業到底要怎麼判斷，要不要留汰役機器

如果你的情境符合這幾點，就值得先留著評估：資料完全不能出門、模型小到能塞進既有記憶體、延遲容忍度高、量少、沒有 SLA，而且真的有人願意維護。這種場合，汰役硬體的價值不一定在算力，而在「先把事情跑起來」。

但如果你要的是併發、24×7、模型要常更新、要留下稽核紀錄、要讓別人接手維運，那就不要把這條路當答案。因為這類需求真正買的是穩定性與可交接性，不是單次 demo 的驚喜。

所以，這次事件真正的訊息不是「PS4 可以當 AI 伺服器」，而是「你的汰役硬體可能還沒真的用完」。真正該算的，是每 token 的總持有成本：電力、維修、越獄風險、維運人力、故障排除時間，而不是帳面上的 FLOPS。把這件事想清楚，你就會知道什麼時候該把舊機器留下來做 PoC，什麼時候該果斷放手。這仍然只是概念驗證（PoC）。
